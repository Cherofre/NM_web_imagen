# 移除背景链路重新评估

日期：2026-10-09。分支：`codex/web-image-editing`，评估基于 `ce7f625` 产品源码。范围为背景移除、KB 2/2.5 失败证据、测试可靠性与本地验收缺口，不泛化为全应用审查。

## 判断

背景移除仍未通过真实验收。核心透明参数符合官方接口；但完整请求含非标准扩展字段，本地诊断与产物验收也有缺口。因此不能简单归因为“渠道坏了”，也不能把换模型当作已经修复。

2.5 那次确定表现为本地 `requests.RequestException` 映射出的 502；具体网络/正文异常没有保留。优先获取图片 POST 的底层异常和渠道对应请求日志，再判定是哪一段失败。现有资料不足以给某个根因分配可信概率。

## 请求与文档核对

实际路径：网页移除背景入口 → FastAPI `/api/generate/gpt-image-2` → `requests.post` → KB 中转 `/v1/images/edits` → 渠道实际图片服务。`/api/status` 和 `/v1/models` 的正常返回只验证读取路径，不能验证最后的图片服务。

- 前端强制一次编辑请求的 `n=1`、edits、auto 尺寸、禁用本次提示增强。后端上传 `image[]`，背景动作追加 `background=transparent`、`output_format=png`。
- [OpenAI 官方图片编辑文档](https://developers.openai.com/api/reference/resources/images/methods/edit) 明确 2.5 sunburst/flare 支持透明背景，透明时选 PNG/WebP。官方能力不能证明带 KB 前缀的代理正确转发、路由或拥有对应能力。
- 更正先前“请求符合官方文档”的过宽表述：**核心透明字段正确，完整请求并非仅含标准字段**。当前 `app.py:5195` 还附带 `enhance_prompt=False`，官方字段清单没有该参数。兼容渠道可接收，严格渠道可能拒绝。后端只在匹配 Unknown parameter/Unrecognized request argument 时删除该可选字段重试；不能覆盖所有拒绝文案。
- 本地准备 multipart 请求（不发送）已确认中文模型名称 UTF-8 保留、`image[]` 字段存在、Content-Length 与实际正文长度一致，False 会编码为表单文本 `False`。未发现这些基础序列化步骤的错误；没有实际捕获此前网络线上传包。
- 只读确认同地址的本地连接只有一个、是当前活动配置，避免选错同地址条目的测试偏差。沿用本地现有密钥，没有从截图读取密钥，没有写配置。

## 已复现的本地问题

| 优先级 | 问题与代码位置 | 离线证据 | 影响与建议 |
| --- | --- | --- | --- |
| P1 | 移除背景缺少实际透明产物验收；`app.py:5504` 用 `bool(images)` 判成功 | 渠道声明 transparent/png 但返回全不透明 PNG，实际透明像素 0/1024，仍 HTTP 200、ok=true；返回 JPEG 也 ok=true | 容易把普通图片当抠图成功。应读取真实格式与 Alpha、识别全不透明/全透明异常；保留返回文件并明确标为未达到透明要求，不自动重发。Alpha 合格后仍需人工验主体/边缘 |
| P1 | 传输错误诊断过于统一；`app.py:5299` | ConnectionError、ChunkedEncodingError、ContentDecodingError 均 502 / E_UPSTREAM_NETWORK / 同一句“无法连接” | 连接中断与拿到响应后正文出错无法区分。应记录固定分类、异常类型/有限原因链、耗时、是否收到响应与安全请求标识；不记录请求头、密钥、完整正文或原始异常字符串 |
| P2 | 背景请求包含扩展字段；`app.py:5195` | 真实请求包装器和离线序列化均确认 enhance_prompt=False | 为旧 400 的兼容性候选，尚非已定位原因。建议明确官方路径的最小请求与渠道扩展行为，不依靠泛化重试来验证。不能把它推断成这次 502 的直接原因 |
| P2 | 一次提交可能产生多次上游调用；`app.py:5351` | 两次 503 后第三次返回图片，n=1 的单次提交产生 3 次 mock POST | 限额实测须统计实际网络调用；一般生图的重试语义另行评估。当前 2.5 测试有一次请求硬限制，实际没有重试；此前 5+3 是应用提交次数，不能宣称等于 8 次上游网络调用 |

这些是现有实现/验收的确定缺口，**不能用它们解释未捕获的历史异常**。本轮评估未修改产品代码，避免在未定因时改变渠道行为。

## 各种原因的证据强弱

| 候选原因 | 目前证据 | 结论 |
| --- | --- | --- |
| 模型名拼错或不在清单 | `/v1/models` 列出准确 KB 2.5 名称；UTF-8 准备请求正确 | 未发现此问题；列表可见不等于该模型生成权限/服务正常 |
| 透明参数拼写/格式组合错误 | transparent + png、edits、有效原图，与官方核心规则相符 | 未发现；仍保留渠道扩展字段兼容风险 |
| KB 2.5 不支持透明 | 官方支持，实际 KB 无明确拒绝响应 | 不能成立为已确认原因 |
| 图片服务链路中断、上传/返回阶段异常 | requests 请求异常，24.28 秒未取得可用完整响应；状态/模型读取正常 | 优先定位的范围，不能具体归责中转或实际上游 |
| 本机环境代理影响 | 无相关代理环境变量，requests 对该地址无有效环境代理 | 未发现环境代理原因，不能排除其他网络设备 |
| 300 秒设置太短 | 2.5 本次 24.28 秒退出，走 RequestException 分支；Timeout 独立映射 504 | 没有证据支持调大本地 300 秒能解决；中间层超时/响应读取异常仍未知 |
| 原图失效或所有 edits 都不能用 | 同一原图/连接的 KB 2 两种局部修改此前实际成功 | 降低此类怀疑；带遮罩与不带遮罩、模型和字段不同，仍无法完全排除特定路径限制 |

旧 KB 2 的约 9.28 秒 HTTP 400 与新 KB 2.5 的约 24.28 秒本地 502 分开处理。前者有 HTTP 拒绝但原文丢失；后者没有保存异常子类型。不将两者拼成单一根因。

## 验证和测试边界

- 本轮 **0 次真实图片 POST**。所有生成调用均在本地 mock 中完成，真实 HTTP 只读取本机配置。
- 10 个离线场景、9 个判断均复现，结果 `.runtime/background-review-20261009/offline-review.json`；这验证的是上述现状/缺口，**不是修复通过**。
- 既有安全边界回归重新运行 **74/74**；核心拒绝分类、参数保护、秘密隔离仍通过。未改产品代码，不重复完整回归、构建和打包。
- 透明 mock PNG 的 960/1024 透明像素能原样保存和读取，说明本地保存路径没有普遍丢弃 Alpha。未验复杂边缘或真实透明产物。
- 2.5 实测通过最新源码 ASGI、隔离历史运行，7861 的旧进程没有重启；并非最新 UI/原生窗口/已发布包验收。
- 新测试包装器已能捕获未来请求的脱敏底层异常；用户应用本身尚未补齐上述分类/验收。历史缺失数据无法追补。

## 推荐处理顺序

1. 先补应用的安全传输分类和真实 Alpha 验收，以本地 mock 验证，无需耗用生图额度。保留旧 error_code 与秘密隔离，不把透明参数删掉来伪装成功。
2. 核清最小标准背景请求与扩展参数策略，单次有上限；不主动换渠道、不静默降级为不透明结果。
3. 需要重新实测时，一次 n=1，禁止自动重试，记录安全请求标识/异常分类/耗时；明确消费预算。若成功，查看实际 Alpha、主体、半透明边缘；若失败，按具体分类请求渠道侧对应记录。
4. 完成真实成功样本和 UI/运行产物验收后，才将移除背景标为稳定。当前不宜对该功能作稳定保证。
