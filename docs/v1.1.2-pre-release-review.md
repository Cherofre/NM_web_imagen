## 已确认问题

### F1 · P1 · 导入同 ID 配置会把本机 Key 绑定到不同地址

- 位置：`studio-web/src/configTransfer.ts:225-233`。
- 触发：本机 `gpt-image-2-default` 使用地址 A 和 Key A；导入另一台机器导出的同 ID 配置，其地址为 B。
- 实际：优先按 ID 合并，保留 Key A，却用导入表单覆盖地址为 B；导入随后自动保存。下一次读取模型、诊断或生成会把本机 Key 发给 B。不同机器的默认 ID 相同，普通分享也能触发，不需要文件携带密钥。
- 建议：只有连接身份一致时才能复用本机 Key；跨地址的同 ID 档案应作为新的无 Key 档案导入，或明确处理地址冲突。覆盖同名 ID 不能隐式改变密钥的接收方。

### F2 · P1 · 保存配置漏掉共用标记和 Gemini 模型清单

- 位置：`studio-web/src/App.tsx:3307-3322`。
- 触发：启用共用连接、读取 Gemini 模型列表，再点击保存并重启。
- 实际：`saveConfig` 手工构造的 GPT/Gemini 表单都没有 `credential_ref`，Gemini 还没有 `model_type_options`。`buildConfigPayload` 用这些表单替换活动档案，因此档案列表也不能补救；重启后共用关系和 Gemini 清单丢失。
- 建议：补齐保存字段，并覆盖“实际 UI 保存请求 → 后端规范化 → 重载”的往返测试。现有导入导出帮助函数测试不能证明保存按钮完整。

### F3 · P1 · 共用连接缺乏可靠配对，切换配置会改写无关档案

- 位置：`studio-web/src/configProfiles.ts:130-146`、`studio-web/src/App.tsx:2702-2723`、`studio-web/src/sharedCredentials.ts:152-156`。
- 触发一：从已共用的 GPT 档案 A 切换到后端保存的独立档案 B。后端会省略空 `credential_ref`；快照未清除此字段，因此 B 继承 A 的 `shared`，继而把 B 的地址和 Key 写入另一引擎仍在使用的 A。
- 触发二：另一侧活动档案已属于别的共用连接时，新连接勾选共用；`findSharedPartner` 仅凭“当前活动且已共用”就把它当作配对档案，即使名字不同，后续会覆盖它。
- 实际：独立配置意外变成共用配置，另一侧已有连接被修改，保存后持久化。
- 建议：切换时明确重置缺失的共用字段；用明确配对身份定位另一侧档案，不能把“另一侧当前活动”当成配对依据；新增连接不得覆盖别的共用对。

### F4 · P2 · Gemini 配置切换继承上一地址的模型清单

- 位置：`studio-web/src/App.tsx:2704`。
- 触发：Gemini 配置 A 已读取模型清单，切换到从未读取过清单的 B。
- 实际：Gemini 分支直接合并 `{ ...bananaForm, ...profile.form }`，目标缺少 `model_type_options` 时保留 A 的值。B 会显示不属于其地址的模型，选择后可能向 B 发出无效模型请求。
- 建议：两种引擎统一采用按档案隔离的快照规则，包含 Gemini 的模型清单字段。

### F5 · P2 · 异步模型列表结果会落到已切换的配置

- 位置：`studio-web/src/App.tsx:2917-2926`。
- 触发：在配置 A 点击读取模型，在请求完成前切换到 B，或修改地址/Key。
- 实际：请求使用闭包里的 A 凭据，响应却通过函数式 setter 写入当前 B 表单；没有核对档案 ID、地址、Key 或请求代次。GPT 生图、聊天及 Gemini 共用这条路径。
- 建议：请求绑定档案与连接快照；返回时校验身份，过期结果丢弃或只更新原档案。覆盖延迟响应期间切换和修改连接的测试。
